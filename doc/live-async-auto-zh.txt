FFmpeg 7.0.3 按压力自适应解码并行度：实现与接入
=============================================

自定义 API 第 2 版，libavcodec 61.5.100。自动控制是显式开启的实验功能。
普通旧接口和未开启自动模式的 async owner 继续保持各自原有行为。
测试证据、吞吐与时延以 tools/live-async/validation/ 中对应版本的报告为准。

1. 最小接入：每路不再按码率/分辨率选择线程数
------------------------------------------
解码器打开时统一指定 thread_count 上限，例如 12，并选择 FF_THREAD_FRAME。
按 live-async-guide-zh.txt 创建 owner，在任何输入/EOF 之前增加一次调用：

  ret = avcodec_async_enable_auto(owner, 0, NULL);
  if (ret < 0) { /* 按业务初始化失败路径清理 */ }

0 表示默认最低目标为 2；最低/最高目标还会受共享预算容量约束。
最大目标不超过已经分配的线程数。线程和参考上下文保持存在，动态变化的是
允许同时派发的在途任务数；空闲线程休眠，不按压力反复销毁/重建线程。
不要运行中修改 AVCodecContext.thread_count，也不要为调度 flush/重开解码器。
启用只能进行一次，必须在首次输入前；它是初始化操作，可以分配内存。

budget=NULL 使用库内进程默认预算，供同进程所有默认自动 owner 共享。
预算约为 av_cpu_count() 的 3/4，至少 1、最多 256；它不保证识别部署系统的
所有 CPU quota，也不保证剩余资源足够 filter/编码。可在部署时显式指定一次。

2. 同进程多路和跨进程共用预算
----------------------------
进程初始化一次，后续每路开启自动模式时复用同一个 handle：

  AVCodecAsyncBudget *budget = NULL;
  ret = avcodec_async_budget_create(&budget, 12, "live-decode");
  if (ret < 0) { /* 初始化失败 */ }
  /* 每路完成 avcodec_async_create 后： */
  ret = avcodec_async_enable_auto(owner, 0, budget);
  /* 所有 owner 都独立持有引用，应用不用 handle 后即可： */
  avcodec_async_budget_free(&budget);

name=NULL：匿名预算，仅同进程内复用该 handle 的 owner 共享。
name 非 NULL：Linux 命名预算，同 UID、同 /dev/shm 文件命名空间内，相同名字
和容量的所有进程共享。名字只能是 1..64 个字母、数字、下划线或短横线。
不同名字、不同 UID 或不同共享内存挂载各自独立。跨容器需共享对应 /dev/shm 挂载。
Windows 仅支持匿名/进程默认预算，命名预算返回 ENOSYS。

同组容量必须一致，不一致直接 EINVAL；容量不支持在线修改。滚动升级保持组名
和容量不变。变更容量应先停止所有相关成员，再清理该组文件/更换组名。
不要在旧组仍运行时让部分成员切换到独立的新组，然后误认为仍有同一硬上限。

命名组使用 /dev/shm/ffmpeg-async-<uid>-<name>.meta 和各个 .slot 文件，权限 0600。
每个额度是一个独占文件锁；进程死亡或最后一个相应文件描述符关闭时由内核
释放。无心跳超时回收，不依赖 PID 身份推断。禁止删除活跃组的文件，否则会
产生相同名字但不同 inode 的独立预算。文件故意保留供后续进程复用。
不要 fork 后继续持有活跃 decoder/budget；正常 fork+exec 会关闭 CLOEXEC 描述符。

预算限制的是参与 owner 的未完成帧任务（含 setup/参考等待），不是 CPU 时间。
filter、编码器、旧接口和未参与该预算的 decoder 不计入其中。它不保证每路的
实时性或严格跨进程公平性，长期超载仍要靠既有背压/业务容量管理。

3. 当前控制器实际做什么
----------------------
每 100 ms 观察输入积压、在途任务使用情况和非 drain 解码回调的完成速率。
持续积压时增加目标，通常每次 +2；对候选目标观察至少 250 ms。连续积压且
未受预算/下游干扰时，完成速率未改善约 3% 就回退，冷却后可试探更大步长，
避免简单地停在某个线程数平台。它不是全局最优吞吐搜索器。
持续低需求且在途峰值低于目标的一半时，每约 1 秒收缩 2，直到最低目标。
下游输出队列满时不继续扩张；始终优先退休已完成任务，再决定是否派发。

所有预算获取、派发和控制都在协调线程。前台 send/receive 仅做原来的短队列
锁与引用操作，不等待额度、解码或参考帧。Linux 跨进程额度释放不能直接唤醒
另一进程的条件变量，因此预算争用时协调线程至多约每 2 ms 重试；这不是忙等。
已完成工作即使因下游阻塞尚未取走，也会归还共享额度。free 在 worker 全部
退出后释放剩余额度。flush 保留配置和历史计数，不重新分配线程。

控制器不直接读取码率/分辨率、系统 CPU PSI 或 cgroup 负载；外部竞争通过实际
完成速率间接体现。配置一次解码任务预算，仍需为 filter/编码和其它服务留资源。
自动模式不会擅自丢帧、跳过参考依赖或绕过 B 帧显示顺序来伪造低时延。

4. 可观测与故障判断
------------------
avcodec_async_get_auto_stats 返回协调线程的近似快照：
  minimum/maximum/target/peak_target：受预算约束的目标范围和目标峰值。
  budget_slots：参与预算的容量；busy/leased：未完成任务/保守持有额度。
  inflight：已派发未退休任务，可能包含已完成但等待顺序/下游的任务。
  input_queue/output_queue：owner 队列深度。
  increases/decreases/probe_rollbacks：升降和无增益回退次数。
  budget_waits：额度申请失败次数，并非等待微秒数。
  completed：非 drain 解码回调完成数，并非用户已经取出的 AVFrame 数。

原 AVCodecAsyncStats 结构未扩展，避免破坏第 1 版调用者的结构体大小。
回调重叠峰值、目标并行度、预算容量都不等于物理 CPU 利用率；吞吐证据还应
结合逻辑核当量（进程 CPU 时间 / 墙钟时间）和按计划到达计算的真实积压。

5. 验证与复现
-------------
test-auto.py：预算 1/2/4/12、H.264/HEVC、1080p/4K、3/7 B 的原版逐帧像素和
元数据比较；多 owner、默认预算、独立句柄、下游暂停、前台 gate、非法参数、
进程容量冲突、SIGKILL 后额度回收、两个进程并发和长样本正确性。
auto_lifetime_test：8 个并发调用者共 160 次默认预算创建/活动中关闭。
test-auto.py --performance：固定上限与自动模式的串行供包/吞吐测试，以及
480 帧样本多次回放的低→高→低压力过程；性能轮不拷贝/哈希像素。
test-async.sh：FFMPEG_LIVE_AUTO_MIN=2 时在自动模式重跑原有生命周期测试。
地址消毒器使用独立禁 asm 构建；它验证内存/泄漏，不证明不存在数据竞争。

默认目录示例：
  python3 tools/live-async/test-auto.py --work /path/to/work
  python3 tools/live-async/test-auto.py --work /path/to/work --performance

不要把短期合成样本测试当作整机多路生产容量或硬实时保证。部署时以实际码流、
完整 filter/编码链及目标进程/容器布局验收。
